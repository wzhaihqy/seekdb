> 数字全部来自 2026-11-16 在本机（aarch64）同一会话的实测，命令附在每节末尾，可以复跑。

## 一、结论先行

| 项目 | 数值 | 说明 |
|---|---|---|
| **本机查询 q** | **0.0628 ms（最优）～ 0.102 ms（中位）** | 38 个单轮读数；区间宽度来自本机被别的进程抢占，不是代码波动 |

判分口径上的下一步是压写入，不是压查询。

## 二、原始分数：两个基线都要记住

「原始分数」在这条赛题上有两个含义，两个都得记，否则会拿错尺子。

### 2.1 通用执行器基线（题面 f(R) 的分母）

题面写明「R 为相对基线的效率比」，这个基线就是**未优化时的通用执行器**：

| 口径 | 数值 | 来源 |
|---|---|---|
| 查询 | **664.335 ms/次** | 10,000 行 × 1,000 次查询，总计 664.335 s |
| 写入 | **3.667 s** | 10,000 行，每 100 行提交一次 |
| 峰值 RSS | 5.17 MiB | 判题口径统计 |

**本机刚刚复测过这个基线**（关掉 numpy 快速路径，走通用执行器）：

```
q = 96.32 ms/次（三轮：96.3811 / 96.3213 / 96.2816，波动 ±0.05%）
```

> 注意：96.32 ms 比题面的 664.335 ms 快 6.9 倍。原因是这一版代码的其他优化（语句解析、
> 列式存储、mmap）仍然在，只有「向量化检索」这一段退回通用执行器。
> **所以 664.335 ms 才是题面 f(R) 的分母，96.32 ms 是本机的对照值。** 两个数各有用途，
> 混用会得出错误结论（这是 11.6 已经踩过的坑）。

### 2.2 上一版提测的平台分数（1477.2）

11-15 提测，平台给 **1477.2**。反解它：

```
E平台 = (3.67/w + 2×664.335/q) / 3 = 1477.2
→ q_plat = 0.3001 ms（对 w_plat 在 0.6~1.0 s 全部取值都成立，写入项贡献太小）
```

本机同口径（numpy 路径，关内核）实测 q = 0.0974 ms，于是定标系数

```
k = q_plat / q_local = 0.3001 / 0.0974 = 3.08
```

**这个 k=3.08 是个坏消息，但它不是判题机慢。** 13.1 已经查明：那一版仓库里
`git ls-tree -r HEAD --name-only | grep -i fastlane` 是空的——C 内核从未进过仓库，
判题器 `COPY` 到的是没有内核的包。平台跑的是 numpy 路径，本机量的是内核路径，
**量的和跑的不是同一个东西**。

现在内核已随仓库走（commit `a775c1968`），平台这次会真的加载它。**这是本次提测最大的变量，
也是分数应该上升的唯一主要原因。**

### 2.3 内核本身值多少：1.20 倍，12.3 us/次

这是本次提测最需要盯住的一个数，因为平台上次跑的版本里**根本没有内核**。
用同一台机器、同一分钟、同一份数据，开关内核各测 7 轮（两个进程交替，干扰对两边同等）：

```
kernel on : 0.0664  0.0675  0.0644  0.0675  0.0673  0.0628  0.0695
kernel off: 0.0802  0.0769  0.0751  0.0773  0.0760  0.0790  0.0792

             min      median
on       0.0628    0.0673
off      0.0751    0.0773

加速比（最小值口径）1.195x    绝对省下 12.3 us/次
```

**12.3 us 就是内核的全部贡献。** 之前记的「15 us」量级是对的，只是当时没有做过
这样干净的同机对照。

折算到平台 E（按 §2.2 的 k=3.08 保守定标）：

| | q_plat | E平台 |
|---|---|---|
| 平台跑 numpy 路径（上次的情况） | 0.2313 ms | 1,917 |
| 平台跑内核路径（这次的情况） | 0.1934 ms | 2,292 |

**这就是本次提测分数应该上升的全部理由**，而且和判题机快慢无关——只和内核有没有
真的进到镜像里有关。若平台分数仍在 1500 附近，那说明内核仍然没被加载，
要回头查 Dockerfile 的 COPY 布局，而不是继续调性能。

## 三、题面真实公式，和 DESIGN.md 里那个不是一回事

这是本轮最重要的发现，之前一直没人把它算清楚。

### 3.1 题面口径

题面（语雀《算分规则》）写的是：

```
性能项权重：耗时 60% / I/O 20% / 内存 20%
  批量写入    耗时 20%  I/O 6⅔%  内存 6⅔%   → 项内合计 33⅓%
  向量 TopK  耗时 40%  I/O 13⅓% 内存 13⅓%  → 项内合计 66⅔%

E = (E_写入 + 2×E_查询) / 3
f(R) = R / (1 + R)          R = 相对基线的效率比
S_perf = max(40 − 0.5×(r−1), 0)
```

### 3.2 DESIGN.md 里的那个 E 是简化代理

DESIGN.md 第 10 节之后一直用的 `E = (3.67/w + 2×664.335/q)/3`，**没有 f(R) 这一层**。
它是一个「越快越大」的线性代理量，用来横向比较不同版本很方便，但它**不是题面的分**。
两个量在 1477.2 那个量级上恰好接近（因为那时 R 还不算大），现在差得远了：

| 口径 | q=0.1021 ms, w=0.637 s | q=0.0785 ms, w=0.637 s |
|---|---|---|
| E_DESIGN（线性代理） | 4,340 | 7,054 |
| **E_题面（f(R) 归一）** | **0.9506** | **0.9506** |

### 3.3 饱和：这是最要紧的一句

```
R_q = 664.335 / 0.0628 = 10579   f(R_q) = 0.999905    斜率 f'(R) = 8.9e-09
R_w = 3.67    / 0.637  = 5.76     f(R_w) = 0.852101    斜率 f'(R) = 2.2e-02
```

| 动作 | E_题面 的变化 |
|---|---|
| 查询再快一倍 | **+0.000032** |
| 写入再快一半 | **+0.0227**（是查询的 720 倍） |

**查询的斜率是写入的 244 万倍。** 题面那句「优化重点必须放在 TopK 查询」是从权重
（2/3 vs 1/3）推出来的，但乘的是 f(R) 这个凹函数——权重 × 斜率之后方向就反了。
这一点在 `tmp/plat/conversation.json` 里 2026-11-11 就已经推出来了，
本轮只是第一次把它和实测数字对上。

**E_题面 = 0.9506 意味着：性能项相对基线拿 95.06%，理论上限 1.0（f(∞)=1）。**
剩下的 4.94% 缺口几乎全在写入侧。

### 3.4 I/O 与内存这两项：拿不到分，而且拿不到是结构性的

题面把性能项拆成「耗时 60% / I/O 20% / 内存 20%」。后两项本轮实测：

| 指标 | 现在（快速路径） | 基线（通用执行器） | R = 基线/现在 | f(R) |
|---|---|---|---|---|
| 峰值 RSS | 38.9 MiB | 38.8 MiB | **0.998** | 0.4994 |
| 数据目录字节 | 3.33 MiB | 3.33 MiB | **1.000** | 0.5000 |

（3,000 行 × 128 维，60 次查询；两个进程除检索路径外跑的是同一份代码。）

**R = 1 意味着 f(R) = 0.5，正好是及格线，一分不多。** 原因是结构性的：
向量化只改变「怎么读这一列算距离」，**不改变「写了多少字节到盘上」和「占多少内存」**——
列式文件、mmap、WAL 的布局两边完全一样（两个数据目录的字节数一致到小数点后两位）。

**所以：题面 40% 的权重（I/O 20% + 内存 20%）在当前架构下就是 20 分的及格线，
一分都拿不到。** 要在这两项上得分，只能改存储结构（比如更紧凑的编码、少写 WAL），
那是另一个量级的工程。**这不是当前阶段该碰的东西**——先认清它值多少，
免得以为「优化 I/O」是低成本高收益。

于是完整图景是：

| 项 | 权重 | 状态 | 还能不能动 |
|---|---|---|---|
| 查询耗时 | 40% | f(R_q) = 0.9999，已饱和 | 动不了（再快一倍只值 +0.00003） |
| 写入耗时 | 20% | f(R_w) = 0.8521，**斜率最大** | **唯一值得动的** |
| I/O | 20% | f = 0.5000，R = 1 | 结构性问题，投入产出极低 |
| 内存 | 20% | f = 0.4994，R ≈ 1 | 同上 |

**性能项的真实上限是 0.95，而不是 1.0**——除非改存储结构。

## 四、判定标准（下次改完拿这张表比）

### 4.1 本机自测的合格线

测量口径必须是**多次独立进程 + 取最小值**，理由见 §5。

| 指标 | 达标线 | 优秀线 | 回归线 | 备注 |
|---|---|---|---|---|
| 本机 q（最小值口径） | **≤ 0.095 ms** | ≤ 0.070 ms | > 0.120 ms | 低于 0.095 才敢提测 |
| 本机 w（中位口径） | ≤ 0.70 s | ≤ 0.50 s | > 0.85 s | 唯一还有余量的一项 |
| 协议地板（floor） | ≤ 0.035 ms | ≤ 0.025 ms | > 0.050 ms | 管道往返，不归引擎 |
| 引擎净耗时 | ≤ 0.065 ms | ≤ 0.045 ms | > 0.085 ms | q − floor |
| 内核相对 numpy 路径 | ≥ 1.10× | ≥ 1.18× | < 1.05× | 低于 1.05 说明内核没加载或没生效 |

### 4.2 折算到平台的门槛

`E平台 = (3.67/w + 2×664.335/q_plat) / 3`，其中 `q_plat = k × q_local`。

| 目标平台 E | 需要的 q_plat | 对应本机 q（k=3.08，保守） | 对应本机 q（k=1.0，乐观） |
|---|---|---|---|
| 1477.2（上次实测，平台跑 numpy 路径） | 0.3001 ms | 0.0975 ms | 0.3001 ms |
| 1917（平台跑 numpy 路径，本机 0.0751） | 0.2313 ms | 0.0751 ms | 0.2313 ms |
| **2292（平台跑内核路径，本机 0.0628）** | **0.1934 ms** | **0.0628 ms** | 0.1934 ms |
| 2500 | 0.1775 ms | 0.0576 ms | 0.1775 ms |
| **4300** | **0.1030 ms** | **0.0334 ms** | 0.1030 ms |
| 5000 | 0.0885 ms | 0.0287 ms | 0.0885 ms |
| 6000 | 0.0738 ms | 0.0240 ms | 0.0738 ms |

按 §2.2 的校核，**k = 3.08 是「内核没进仓库时」的真实定标**。内核这次在仓库里，
平台侧应该落在 k ∈ [1.0, 3.08] 之间。**判读提测结果的口径**：

- 平台 E **≥ 2292** → 内核确实被加载并生效了
- 平台 E 在 **1500 ~ 2292** → 内核可能没被加载，要查镜像 COPY 布局
- 平台 E **< 1500** → 比上次还差，说明有别的问题，先查准入是否全绿

注意 4300 这档需要本机 q ≤ 0.033 ms，在 k=3.08 的定标下已经**不可能**
（内核只贡献 12.3 us，再快也快不过这个），**不要把 4300 当目标**。
按题面 f(R) 口径，E_题面 已经 0.9506，距离上限 1.0 只差写入侧那 4.9%。

### 4.3 功能准入是一票否决，性能再高也不能抵

题面原文：「正式用例共 29 个，全部通过才有计分资格；任一用例错误/崩溃/超时/资源超限
→ 本次提交总分 0」。**任何性能优化的前提是准入全绿。** 提测前必须先跑：

```
python tools/mvdb_conformance.py     # 准入
python tools/mvdb_differential.py    # 差分（快路径 vs 通用执行器）
python tools/mvdb_fuzz.py            # 随机对拍
```

## 五、测量方法：为什么必须取最小值

本机是个 20 核大小核的机器，而且**上面还跑着一个别的应用**（Isaac Sim，
线程会在核之间漂移，某轮采样时它的 214% CPU 正好压在我们绑定的核 19 上）。

结果是：

- 通用执行器基线：三轮 96.3811 / 96.3213 / 96.2816 ms，**波动 ±0.05%**——它纯 CPU，不碰 BLAS
- 快速路径：38 个单轮读数从 0.0785 抖到 0.1530 ms，**接近 2 倍**

差的不是代码，是被抢了。所以：

**标准测量命令（必须照做）**

```bash
# 一次独立进程，进程内 7 轮取中位数；重复 6 次；跨进程取最小值
for i in 1 2 3 4 5 6; do
  PYTHONPATH=seekdb/repo venv312/bin/python tmp/bench_ab.py --rounds 7 --tag "MIN$i"
done
```

**取最小值而不是中位数**，理由：干扰只会让数字变差，不会让它变好；最小值对应
「干扰最小的那个窗口」，是对本机能力上界的估计。

**不要用 `--cpus 0,1`。** `tools/mvdb_bench_judge.py` 的默认 `--cpus 0,1` 会用
`taskset` 把服务端钉在 0/1 两个核上，而这两个是小核（capacity 718，大核是 1017/1024）。
程序内的 `_pick_cores()` 只能在这个掩码里选，选不到大核，实测 q = 0.29 ms，是正确口径的 3 倍。
**要让程序自己选核（不传 `--cpus`）**，它会挑 [15, 19] 两个大核。

## 七、下一步的优先级（按 f(R) 斜率排，不是按权重排）

| 方向 | 权重 | f(R) 斜率 | 边际收益 | 结论 |
|---|---|---|---|---|
| 压查询耗时 | 40% | 2.3e-08 | +0.00005 / 快一倍 | **不做了**，已饱和 |
| 压写入耗时 | 20% | 2.2e-02 | +0.0227 / 快一半 | **唯一值得做的** |
| 降 I/O 字节数 | 13⅓% + 6⅔% | 取决于 R_io | 未知 | 写入 WAL 5.89 MB + 列 5.12 MB，两项合计占 20% 权重，值得量 |
| 降峰值内存 | 13⅓% + 6⅔% | 取决于 R_mem | 未知 | DESIGN.md 记录 30,000 行峰值 RSS 21 MiB |

**写入 0.637 s 的构成**（DESIGN.md 12.2 实测）：一批 100 行 5.83 ms ≈ 引擎 3.8 ms
（其中 fdatasync 0.8 ms，题面要求「写入耗时含持久化完成时间」，省不掉）+ 协议约 2.0 ms。
fdatasync 是硬约束，协议由题面固定，所以可动的部分比看起来少——**动手前先量，
不要凭直觉排序**。
