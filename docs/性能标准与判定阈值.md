## 〇之前、必须先知道的三件事（2026-11-17 补）

### 1. 测性能必须用带 numpy 的解释器，否则量到的是假象

`minivectordb/fastpath.py` 在 numpy 缺席时会让整个查询退回通用执行器
（逐行解码 + 逐行 `l2_distance`）。用没有 numpy 的解释器跑同一份负载：

| 指标 | 无 numpy | 有 numpy（真实） |
|---|---|---|
| 写入 10,000 | 0.729 s | 0.547 s |
| 查询 1,000 | **88.938 s** | **0.109 s** |
| 峰值内存 | 40.5 MiB | 46.6 MiB |

**用错解释器会得出「查询慢 800 倍」的完全错误结论。**
可用的解释器是 `2026-11-14-06-20-42/venv312/bin/python3`（numpy 2.2.3，与判题镜像同版本）。
自检一行：`python3 -c "from minivectordb import fastpath; print(fastpath.available())"`，
必须打印 `True`。

### 2. 判题容器形态下的实测（`--cpus=2 --memory=2g --read-only --network=none`）

| 指标 | 本机判题形态 | 社区自测基准 | 判定 |
|---|---|---|---|
| 写入 10,000 行 | **0.536–0.553 s** | ~2 s | 已快 3.7 倍 |
| 查询 1,000 次 | **0.102–0.123 s** | ~1 s | 已快 8–10 倍 |
| 峰值内存 | 46.6 MiB | ~50 MB | 相当 |

**两条常被提起的优化线索，实测都已经不是瓶颈**：

- *持久化批量落盘*：写入 0.264 s（进程内）里 fsync 占 37.3%（100 次，每次 0.986 ms），
  是写入的最大单项；但写入项在平台公式里只贡献 **0.099%** 的总分
  （`3.67/w` ≈ 1.99，而查询项 ≈ 2007.4），即使把写入再压一半，分数只涨约 2.6。
- *过滤剪枝*：**已经实现**。`engine.py` 的 `_scan_filtered` 在 `ids.size*3 <= total` 时
  只 gather 命中的行再算距离；实测带过滤 0.0412 ms vs 无过滤 0.1411 ms，快 3.4 倍。

### 3. 查询的成本构成（2 核，ms/query）

```
SQL 解析            0.0019   1.4%
向量字面量 C 解析    0.0002   0.1%
向量扫描(GEMV+TopK) 0.1163  82.4%   ← 已贴 BLAS 带宽下限
其余(投影/组装/JSON) 0.0227  16.1%
```

扫描本身占 82%，解析几乎免费。**查询侧没有廉价的大头可挖**，剩余空间要靠改写算法而不是调参数。

基线 `986ff36d3` 最小值 0.0885 ms / 中位 0.1134 ms，当前版最小值 0.0773 ms / 中位 0.0943 ms，

写入侧基线中位 0.750 s、当前版 0.615 s，**1.218 倍，12 组全胜**。

**据此的平台投影**（按 k=2.676 折算）：

当前版 q_local = 0.0773 ms  →  q_plat ≈ 0.2069 ms  →  E平台 ≈ 2143

基线   q_local = 0.0885 ms  →  q_plat ≈ 0.2368 ms  →  E平台 ≈ 1872

> 分母用了不限核的数字，混进了线程配置差异。修正后投影是 **1757～2143**，
> 区间比原来宽，但**上沿更高**。

**必须说清的三件事**：

1. **投影值与上一版基本持平（最乐观 2143 vs 上次实测 1871.7），不是数量级的提升。**

3. **但这不等于性能项没有提升。** 题面真正的 40 分用的是 `f(R)` 归一口径，

## 二、原始分数：两个基线都要记住

「原始分数」在这条赛题上有两个含义，两个都得记，否则会拿错尺子。

### 2.1 通用执行器基线（题面 f(R) 的分母）

题面写明「R 为相对基线的效率比」，这个基线就是**未优化时的通用执行器**：

| 口径 | 数值 | 来源 |
|---|---|---|
| 查询 | **664.335 ms/次** | 10,000 行 × 1,000 次查询，总计 664.335 s |
| 写入 | **3.667 s** | 10,000 行，每 100 行提交一次 |
| 峰值 RSS | 5.17 MiB | 判题口径统计 |

**本机刚刚复测过这个基线**（关掉 numpy 快速路径，走通用执行器）：

```
q = 96.32 ms/次（三轮：96.3811 / 96.3213 / 96.2816，波动 ±0.05%）
```

> 注意：96.32 ms 比题面的 664.335 ms 快 6.9 倍。原因是这一版代码的其他优化（语句解析、
> 列式存储、mmap）仍然在，只有「向量化检索」这一段退回通用执行器。
> **所以 664.335 ms 才是题面 f(R) 的分母，96.32 ms 是本机的对照值。** 两个数各有用途，
> 混用会得出错误结论（这是 11.6 已经踩过的坑）。

### 2.2 平台分数的观测点，以及同形态定标 k

平台历史分数有两个已知观测点，都是"某个 commit 在平台上的实测"：

| commit | 平台分 | 树里有内核？ | 本机 q_local（**不限核**） | 反解 q_plat | k |
|---|---|---|---|---|---|
| `02fedb9cf` | **1477.2** | **没有**（`git ls-tree` 无 `.so`） | 0.0961 ms | 0.3002 ms | 3.12 |
| `986ff36d3` | **1871.704677** | **有**（`.so` 已在树里） | 0.0743 ms | 0.2369 ms | 3.19 |

反解方式（写入项贡献太小，w_plat 取 0.6～1.0 s 全都成立）：

```
E平台 = (3.67/w + 2×664.335/q_plat) / 3
→ q_plat = 2×664.335 / (3×E平台 − 3.67/w)
```

> ⚠️ **上表作废：它把两端的线程配置混在了一起。**
> 分母的 0.0743 ms 是**不限核**测的，而平台跑的是 `--cpus=2` 的容器。
> 慢速比里于是混进了「不限核 vs 2 核」这一项，不只是机器差异。
> 2026-11-17 重做：分母也用判题机形态（绑 2 核 + BLAS=1）测，
> **k = 2.676**，不是 3.19。

#### 同形态定标：k = 2.676

平台容器是 `docker run --cpus=2 --memory=2g`，`Dockerfile` 里写死
`OPENBLAS_NUM_THREADS=2 / OMP_NUM_THREADS=2 / MINIVECTORDB_BLAS_THREADS=2`。
本机要复现这个形态，就绑 2 核并把 BLAS 线程压到 1（容器里 2 线程在 2 个 CPU 上
会互相争抢，本机不限核时 2 线程反而更快）。

**15 组交替对照**，`986ff36d3`（平台 1871.704677）与当前版同分钟交替跑，
干扰同等地落在两边：

```bash
cd /home/wzh_linux/WorkBuddy/2026-11-14-06-20-42
for i in $(seq 1 15); do
  b=$(cd tmp/wt_dot   && OPENBLAS_NUM_THREADS=1 PYTHONPATH=. venv312/bin/python \
        tools/mvdb_bench_judge.py --rows 10000 --queries 1000 --cpus 18,19 --tag "cb_$i" \
        | grep -oE "query 0\.[0-9]+" | grep -oE "0\.[0-9]+")
  c=$(cd seekdb/repo && OPENBLAS_NUM_THREADS=1 PYTHONPATH=. venv312/bin/python \
        tools/mvdb_bench_judge.py --rows 10000 --queries 1000 --cpus 18,19 --tag "cc_$i" \
        | grep -oE "query 0\.[0-9]+" | grep -oE "0\.[0-9]+")
  echo "BASE $b"; echo "CUR  $c"
done
```

结果：

| | 最小值 | p25 | 中位 | 均值 | 最差 |
|---|---|---|---|---|---|
| 基线 `986ff36d3` | 0.0885 ms | 0.0969 ms | 0.1134 ms | 0.1385 ms | 0.2372 ms |
| 当前版 | **0.0773 ms** | **0.0780 ms** | **0.0943 ms** | **0.0956 ms** | 0.1400 ms |

定标（用最小值口径，这是跨进程最稳的统计量）：

```
q_plat = 2×664.335 / (3×1871.704677 − 3.67/0.736) = 0.2368 ms
k      = 0.2368 / 0.0885 = 2.676
```

**这个 k 只在两端口径完全一致时才成立。** 旧的 3.19 高估了 19%，
会让本机数被折算成一个比实际更差的平台数——**方向是自我惩罚**，
但它同时让「还差多少」的估计也偏大。

> **定标的两条纪律，缺一不可：**
> 1. 比值两端必须来自**同一个 commit**。
> 2. 比值两端必须是**同一套运行形态**（同样的核数、同样的 BLAS 线程数）。
>
> 第 2 条是 2026-11-17 才补上的：前一条守住了，后一条一直漏着。

### 2.5 判题机只有 2 个 CPU：这决定了目标可达性

题面写明判题容器是 `docker run --cpus=2 --memory=2g`。**`--cpus` 是 CFS 配额，
不是 CPU 亲和性**——容器里 `os.cpu_count()` 仍然看得到宿主的全部核心，
BLAS 会按可见核数开线程，然后被配额节流。

实测三档（`numpy.dot` 10000×128 的 f32 矩阵向量积）：

| 配置 | dot 耗时 | 有效带宽 |
|---|---|---|
| 绑 2 核 + BLAS=1（判题机形态） | **39.67 us** | — |
| 绑 2 核 + BLAS=2 | 几乎不变 | — |
| 不限核 + BLAS=20（默认） | **14.6 us** | 78 GB/s（已到带宽上限） |

同一份代码的整体查询时间：**不限核 0.0629 ms，绑 2 核 0.0764 ms——差距 21% 全部来自线程数，
不是代码。**

**因此：凡是要外推到平台的数字，必须在 2 核形态下测。**
不限核的数字只能用来找瓶颈方向（本轮就是靠它确认 dot 已到 78 GB/s 带宽上限、
float32 是最优的、没有隐藏拷贝），**不能用来报分数**。

另一个由此得到的硬结论：dot 在 2 核下要 39.67 us，而 2 核下引擎净耗时 0.0525 ms，
协议地板 0.0248 ms。**要靠压 dot 把平台分推到 5000，在 2 核形态下没有物理空间。**

## 三、题面真实公式，和 DESIGN.md 里那个不是一回事

这是本轮最重要的发现，之前一直没人把它算清楚。

### 3.1 题面口径

题面（语雀《算分规则》）写的是：

```
性能项权重：耗时 60% / I/O 20% / 内存 20%
  批量写入    耗时 20%  I/O 6⅔%  内存 6⅔%   → 项内合计 33⅓%
  向量 TopK  耗时 40%  I/O 13⅓% 内存 13⅓%  → 项内合计 66⅔%

E = (E_写入 + 2×E_查询) / 3
f(R) = R / (1 + R)          R = 相对基线的效率比
S_perf = max(40 − 0.5×(r−1), 0)
```

### 3.2 DESIGN.md 里的那个 E 是简化代理

DESIGN.md 第 10 节之后一直用的 `E = (3.67/w + 2×664.335/q)/3`，**没有 f(R) 这一层**。
它是一个「越快越大」的线性代理量，用来横向比较不同版本很方便，但它**不是题面的分**。
两个量在 1477.2 那个量级上恰好接近（因为那时 R 还不算大），现在差得远了：

| 口径 | q=0.1021 ms, w=0.750 s | q=0.0773 ms, w=0.615 s |
|---|---|---|
| E_DESIGN（线性代理） | 4,340 | 8,127 |
| **E_题面（f(R) 归一）** | **0.9506** | **0.9593** |

**这就是这一轮写进分数里的东西**：E_DESIGN 涨了 87%，而 E_题面只涨了 0.0087。
两个口径对同一件事给出的评价差两个数量级——**只有 E_题面是那 40 分**。

### 3.3 饱和：这是最要紧的一句

用本轮实测的中位口径（q=0.0943 ms，w=0.615 s）：

```
R_q = 664.335 / 0.0943 = 7045   f(R_q) = 0.999858    斜率 f'(R) = 2.0e-08
R_w = 3.67    / 0.615  = 5.967   f(R_w) = 0.856376    斜率 f'(R) = 1.4e-02
```

| 动作 | E_题面 的变化 |
|---|---|
| 查询再快一倍 | **+0.000014** |
| 写入再快一半 | **+0.0157**（是查询的 1100 倍） |

**查询的斜率是写入的 70 万倍。** 题面那句「优化重点必须放在 TopK 查询」是从权重
（2/3 vs 1/3）推出来的，但乘的是 f(R) 这个凹函数——权重 × 斜率之后方向就反了。
这一点在 `tmp/plat/conversation.json` 里 2026-11-11 就已经推出来了，
本轮只是第一次把它和实测数字对上。

**E_题面 = 0.9593 意味着：性能项相对基线拿 95.93%，理论上限 1.0（f(∞)=1）。**
剩下的 4.07% 缺口几乎全在写入侧——本轮把它从 0.9506 抬到了 0.9593，
剩下的要动 WAL 或列式布局，是另一个量级的工程。

### 3.4 I/O 与内存这两项：拿不到分，而且拿不到是结构性的

题面把性能项拆成「耗时 60% / I/O 20% / 内存 20%」。后两项本轮实测：

| 指标 | 现在（快速路径） | 基线（通用执行器） | R = 基线/现在 | f(R) |
|---|---|---|---|---|
| 峰值 RSS | 38.9 MiB | 38.8 MiB | **0.998** | 0.4994 |
| 数据目录字节 | 3.33 MiB | 3.33 MiB | **1.000** | 0.5000 |

（3,000 行 × 128 维，60 次查询；两个进程除检索路径外跑的是同一份代码。）

**R = 1 意味着 f(R) = 0.5，正好是及格线，一分不多。** 原因是结构性的：
向量化只改变「怎么读这一列算距离」，**不改变「写了多少字节到盘上」和「占多少内存」**——
列式文件、mmap、WAL 的布局两边完全一样（两个数据目录的字节数一致到小数点后两位）。

**所以：题面 40% 的权重（I/O 20% + 内存 20%）在当前架构下就是 20 分的及格线，
一分都拿不到。** 要在这两项上得分，只能改存储结构（比如更紧凑的编码、少写 WAL），
那是另一个量级的工程。**这不是当前阶段该碰的东西**——先认清它值多少，
免得以为「优化 I/O」是低成本高收益。

于是完整图景是：

| 项 | 权重 | 状态 | 还能不能动 |
|---|---|---|---|
| 查询耗时 | 40% | f(R_q) = 0.9999，已饱和 | 动不了（再快一倍只值 +0.00003） |
| 写入耗时 | 20% | f(R_w) = 0.8521，**斜率最大** | **唯一值得动的** |
| I/O | 20% | f = 0.5000，R = 1 | 结构性问题，投入产出极低 |
| 内存 | 20% | f = 0.4994，R ≈ 1 | 同上 |

**性能项的真实上限是 0.95，而不是 1.0**——除非改存储结构。

## 五、测量方法：为什么必须取最小值

本机是个 20 核大小核的机器，而且**上面还跑着一个别的应用**（Isaac Sim，
线程会在核之间漂移，某轮采样时它的 214% CPU 正好压在我们绑定的核 19 上）。

结果是：

- 通用执行器基线：三轮 96.3811 / 96.3213 / 96.2816 ms，**波动 ±0.05%**——它纯 CPU，不碰 BLAS
- 快速路径：38 个单轮读数从 0.0785 抖到 0.1530 ms，**接近 2 倍**

差的不是代码，是被抢了。所以：

**标准测量命令（必须照做）**

```bash
# 一次独立进程，进程内 7 轮取中位数；重复 6 次；跨进程取最小值
for i in 1 2 3 4 5 6; do
  PYTHONPATH=seekdb/repo venv312/bin/python tmp/bench_ab.py --rounds 7 --tag "MIN$i"
done
```

**取最小值而不是中位数**，理由：干扰只会让数字变差，不会让它变好；最小值对应
「干扰最小的那个窗口」，是对本机能力上界的估计。

**不要用 `--cpus 0,1`。** `tools/mvdb_bench_judge.py` 的默认 `--cpus 0,1` 会用
`taskset` 把服务端钉在 0/1 两个核上，而这两个是小核（capacity 718，大核是 1017/1024）。
程序内的 `_pick_cores()` 只能在这个掩码里选，选不到大核，实测 q = 0.29 ms，是正确口径的 3 倍。
**要让程序自己选核（不传 `--cpus`）**，它会挑 [15, 19] 两个大核。

### 6.1 基准工具输出的三个数，各是什么

`tools/mvdb_bench_judge.py` 现在一次打印三个数，**它们不可互换**：

```
write 0.658 s   query 0.0768 ms/query   protocol floor 0.0241 ms   engine 0.0527 ms
  E local    5769   (this machine's q; optimistic by k)
  E platform 2157   (q_plat = 0.2055 ms = k 2.68 x 0.0768 ms; the number the judge prints)
  E=5000     needs query 0.0331 ms/query on this machine (protocol floor here is 0.0241 ms)
```

| 输出 | 含义 | 能不能当平台分 |
|---|---|---|
| `E local` | 用**本机** q 代进公式 `E=(3.67/w + 2×664.335/q)/3` | **不能**。它乐观了恰好 k 倍，量级会差 3 倍以上 |
| `E platform` | `q_plat = k × q_local`，k 默认 2.676，可用 `--platform-k` 改 | **能**。这是判题机打印的数 |
| `E=5000` | 达到平台分 5000 需要的**本机** q，和协议地板并排打印 | 用来一眼看出缺口，而不是靠推算 |

> **这一版为什么要改**：改之前工具把本机口径的数直接印成 `E estimate 4825`，
> 没有任何标注，很容易被当成平台分读成"已经过 5000"。这正是本项目在 §2.2
> 反复强调的口径混淆，工具自己不该再犯一次。现在三个数分列且各自标注，
> `E=5000` 需要的 0.0331 ms 与协议地板 0.0241 ms 直接并排，缺口在输出里自明。
>
> `--selftest` 会用已知的平台观测点（1871.704677）校验投影公式，
> 容差 0.5% 相对误差——写入项从未在判题机上单独测过，是从本机带过去的，
> 而查询项比写入项大三个数量级，所以 0.5% 是诚实的上界。
> **自检里的观测点也已换成同形态的数字**：两端都是 2 核 + BLAS=1。

### 7.1 本轮写入优化的实测（已完成）

`tools/mvdb_write_pieces.py` 把写入拆成六段，10,000 行 / 100 批：

| 段 | 优化前 | 优化后 | 能不能动 |
|---|---|---|---|
| sync（fdatasync） | 10.22 us/行 | 10.22 us/行 | **不能**，题面要求写入耗时含持久化 |
| flush（物化列文件） | 6.75 us/行 | 6.75 us/行 | 能，但要改存储布局 |
| **parse（SQL → 行）** | **16.73 us/行** | **5.51 us/行** | **本轮压的就是这一段** |
| wal | 2.56 us/行 | 2.56 us/行 | 不能（WAL 是崩溃恢复的保证） |
| coerce（类型转换） | **14.69 us/行** | **0.49 us/行** | **本轮压的就是这一段** |

原来 14.69 us/行 的 coerce 是最大的可动项——判题器的 INSERT 把向量写成
带引号的 `'[...]'`，解析器把它当普通字符串，引擎再逐个数读文本。
现在解析器直接调用 C 内核打包 float32（`fl_parse_vector_any`），
**2.4 us vs 参考实现 12.4 us**，500 组随机字面量逐位一致。

**代价转移过一次**：第一步只是把 numpy 打包塞进解析器，coerce 从 14.69 掉到 0.49，
但 parse 从 2.46 涨到 16.73——**总量没变**。真正的收益来自把打包换成 C 内核。

### 7.2 还没动的

- **flush 6.75 us/行**：逐行 `store.put` → 逐列 `write_at`，还要维护 float64 副本。
  批量接口（一次写一批行）能省掉每行的 dict 查找和函数调用，
  但要动 `store.py` 的写入契约。
- **sync 10.22 us/行**：fdatasync，题面明确「写入耗时含持久化完成时间」，动不了。
- **I/O 与内存两项**：R = 1 是结构性的，除非改存储布局（更紧凑的编码、WAL 压缩）。

> 改存储布局能同时动三项（写入耗时、I/O 字节、峰值内存），但那是另一个量级的工程，
> 且**会碰崩溃恢复**——题面的一票否决项。动之前先把现在的版本提测掉。
