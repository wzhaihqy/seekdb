1. **投影值与上一版基本持平（1900 vs 1871.7），不是数量级的提升。** 原因见 §2.5：

## 二、原始分数：两个基线都要记住

「原始分数」在这条赛题上有两个含义，两个都得记，否则会拿错尺子。

### 2.1 通用执行器基线（题面 f(R) 的分母）

题面写明「R 为相对基线的效率比」，这个基线就是**未优化时的通用执行器**：

| 口径 | 数值 | 来源 |
|---|---|---|
| 查询 | **664.335 ms/次** | 10,000 行 × 1,000 次查询，总计 664.335 s |
| 写入 | **3.667 s** | 10,000 行，每 100 行提交一次 |
| 峰值 RSS | 5.17 MiB | 判题口径统计 |

**本机刚刚复测过这个基线**（关掉 numpy 快速路径，走通用执行器）：

```
q = 96.32 ms/次（三轮：96.3811 / 96.3213 / 96.2816，波动 ±0.05%）
```

> 注意：96.32 ms 比题面的 664.335 ms 快 6.9 倍。原因是这一版代码的其他优化（语句解析、
> 列式存储、mmap）仍然在，只有「向量化检索」这一段退回通用执行器。
> **所以 664.335 ms 才是题面 f(R) 的分母，96.32 ms 是本机的对照值。** 两个数各有用途，
> 混用会得出错误结论（这是 11.6 已经踩过的坑）。

### 2.2 平台分数的三个观测点，以及同版本定标 k

平台历史分数有两个已知观测点，都是"某个 commit 在平台上的实测"：

| commit | 平台分 | 树里有内核？ | 本机 q_local（不限核） | 反解 q_plat | k = q_plat/q_local |
|---|---|---|---|---|---|
| `02fedb9cf` | **1477.2** | **没有**（`git ls-tree` 无 `.so`） | 0.0961 ms | 0.3002 ms | **3.12** |
| `986ff36d3` | **1871.704677** | **有**（`.so` 已在树里） | 0.0743 ms | 0.2369 ms | **3.19** |

反解方式（写入项贡献太小，w_plat 取 0.6～1.0 s 全都成立）：

```
E平台 = (3.67/w + 2×664.335/q_plat) / 3
→ q_plat = 2×664.335 / (3×E平台 − 3.67/w)
```

**两个完全独立的 commit 给出同一个 k ≈ 3.1–3.2**，说明慢速比是**机器属性**，
不是代码属性。这就是把本机数翻译成平台分的换算系数。

> **定标的唯一纪律：比值两端必须来自同一个 commit、同一套配置。**
> 上一轮曾用不同版本的数相除（拿当前版的 0.0961 去比 1477.2 那版的平台数），
> 把代码差异算进了机器差异里，结论是错的。

### 2.3 内核本身值多少：1.20 倍，12.3 us/次

这是本次提测最需要盯住的一个数，因为平台上次跑的版本里**根本没有内核**。
用同一台机器、同一分钟、同一份数据，开关内核各测 7 轮（两个进程交替，干扰对两边同等）：

```
kernel on : 0.0664  0.0675  0.0644  0.0675  0.0673  0.0628  0.0695
kernel off: 0.0802  0.0769  0.0751  0.0773  0.0760  0.0790  0.0792

             min      median
on       0.0628    0.0673
off      0.0751    0.0773

加速比（最小值口径）1.195x    绝对省下 12.3 us/次
```

**12.3 us 就是内核的全部贡献。** 之前记的「15 us」量级是对的，只是当时没有做过
这样干净的同机对照。

折算到平台 E（按 §2.2 的 k=3.08 保守定标）：

| | q_plat | E平台 |
|---|---|---|
| 平台跑 numpy 路径（上次的情况） | 0.2313 ms | 1,917 |
| 平台跑内核路径（这次的情况） | 0.1934 ms | 2,292 |

**这就是本次提测分数应该上升的全部理由**，而且和判题机快慢无关——只和内核有没有
真的进到镜像里有关。若平台分数仍在 1500 附近，那说明内核仍然没被加载，
要回头查 Dockerfile 的 COPY 布局，而不是继续调性能。

### 2.4 当前版 vs 基线：12 组交替对照

单次对照在这个机器上没有意义——本机有别的应用在抢核，同一份代码两次跑能差 2 倍以上。
规程是**交替跑**（干扰同等地落在两边）+ **跨进程取最小值**。

```bash
cd /home/wzh_linux/WorkBuddy/2026-11-14-06-20-42
for i in $(seq 1 12); do
  b=$(cd tmp/wt_dot && OPENBLAS_NUM_THREADS=1 PYTHONPATH=. venv312/bin/python \
        tools/mvdb_bench_judge.py --rows 10000 --queries 1000 --cpus 18,19 --tag "m2_b_$i" \
        | grep -oE "query 0\.[0-9]+" | grep -oE "0\.[0-9]+")
  c=$(cd seekdb/repo && OPENBLAS_NUM_THREADS=1 PYTHONPATH=. venv312/bin/python \
        tools/mvdb_bench_judge.py --rows 10000 --queries 1000 --cpus 18,19 --tag "m2_c_$i" \
        | grep -oE "query 0\.[0-9]+" | grep -oE "0\.[0-9]+")
  echo "$b $c"
done
```

结果：

| | 最小值 | 中位 | 均值 | 最差 |
|---|---|---|---|---|
| 基线 `986ff36d3` | 0.0834 ms | 0.1346 ms | 0.2205 ms | 0.5640 ms |
| **当前工作树** | **0.0761 ms** | **0.0877 ms** | **0.0990 ms** | 0.1825 ms |
| **比值** | **1.096×** | **1.536×** | 2.228× | — |

12 组里当前版赢 **10 组**。基线的尾部重得多（最差 0.5640 ms，当前版没有超过 0.1825 ms），
这来自当前版把协议 I/O 换成了字节流、ctypes 指针做了缓存。

**两个口径都要看**：最小值口径回答"代码本身能有多快"，中位口径回答"实际跑起来平均快多少"。
平台取的是三轮中位数，所以中位口径更接近平台的判读方式。

### 2.5 判题机只有 2 个 CPU：这决定了目标可达性

题面写明判题容器是 `docker run --cpus=2 --memory=2g`。**`--cpus` 是 CFS 配额，
不是 CPU 亲和性**——容器里 `os.cpu_count()` 仍然看得到宿主的全部核心，
BLAS 会按可见核数开线程，然后被配额节流。

实测三档（`numpy.dot` 10000×128 的 f32 矩阵向量积）：

| 配置 | dot 耗时 | 有效带宽 |
|---|---|---|
| 绑 2 核 + BLAS=1（判题机形态） | **39.67 us** | — |
| 绑 2 核 + BLAS=2 | 几乎不变 | — |
| 不限核 + BLAS=20（默认） | **14.6 us** | 78 GB/s（已到带宽上限） |

同一份代码的整体查询时间：**不限核 0.0629 ms，绑 2 核 0.0764 ms——差距 21% 全部来自线程数，
不是代码。**

**因此：凡是要外推到平台的数字，必须在 2 核形态下测。**
不限核的数字只能用来找瓶颈方向（本轮就是靠它确认 dot 已到 78 GB/s 带宽上限、
float32 是最优的、没有隐藏拷贝），**不能用来报分数**。

另一个由此得到的硬结论：dot 在 2 核下要 39.67 us，而 2 核下引擎净耗时 0.0508 ms，
协议地板 0.0248 ms。**要靠压 dot 把平台分推到 5000，在 2 核形态下没有物理空间。**

## 三、题面真实公式，和 DESIGN.md 里那个不是一回事

这是本轮最重要的发现，之前一直没人把它算清楚。

### 3.1 题面口径

题面（语雀《算分规则》）写的是：

```
性能项权重：耗时 60% / I/O 20% / 内存 20%
  批量写入    耗时 20%  I/O 6⅔%  内存 6⅔%   → 项内合计 33⅓%
  向量 TopK  耗时 40%  I/O 13⅓% 内存 13⅓%  → 项内合计 66⅔%

E = (E_写入 + 2×E_查询) / 3
f(R) = R / (1 + R)          R = 相对基线的效率比
S_perf = max(40 − 0.5×(r−1), 0)
```

### 3.2 DESIGN.md 里的那个 E 是简化代理

DESIGN.md 第 10 节之后一直用的 `E = (3.67/w + 2×664.335/q)/3`，**没有 f(R) 这一层**。
它是一个「越快越大」的线性代理量，用来横向比较不同版本很方便，但它**不是题面的分**。
两个量在 1477.2 那个量级上恰好接近（因为那时 R 还不算大），现在差得远了：

| 口径 | q=0.1021 ms, w=0.637 s | q=0.0785 ms, w=0.637 s |
|---|---|---|
| E_DESIGN（线性代理） | 4,340 | 7,054 |
| **E_题面（f(R) 归一）** | **0.9506** | **0.9506** |

### 3.3 饱和：这是最要紧的一句

```
R_q = 664.335 / 0.0628 = 10579   f(R_q) = 0.999905    斜率 f'(R) = 8.9e-09
R_w = 3.67    / 0.637  = 5.76     f(R_w) = 0.852101    斜率 f'(R) = 2.2e-02
```

| 动作 | E_题面 的变化 |
|---|---|
| 查询再快一倍 | **+0.000032** |
| 写入再快一半 | **+0.0227**（是查询的 720 倍） |

**查询的斜率是写入的 244 万倍。** 题面那句「优化重点必须放在 TopK 查询」是从权重
（2/3 vs 1/3）推出来的，但乘的是 f(R) 这个凹函数——权重 × 斜率之后方向就反了。
这一点在 `tmp/plat/conversation.json` 里 2026-11-11 就已经推出来了，
本轮只是第一次把它和实测数字对上。

**E_题面 = 0.9506 意味着：性能项相对基线拿 95.06%，理论上限 1.0（f(∞)=1）。**
剩下的 4.94% 缺口几乎全在写入侧。

### 3.4 I/O 与内存这两项：拿不到分，而且拿不到是结构性的

题面把性能项拆成「耗时 60% / I/O 20% / 内存 20%」。后两项本轮实测：

| 指标 | 现在（快速路径） | 基线（通用执行器） | R = 基线/现在 | f(R) |
|---|---|---|---|---|
| 峰值 RSS | 38.9 MiB | 38.8 MiB | **0.998** | 0.4994 |
| 数据目录字节 | 3.33 MiB | 3.33 MiB | **1.000** | 0.5000 |

（3,000 行 × 128 维，60 次查询；两个进程除检索路径外跑的是同一份代码。）

**R = 1 意味着 f(R) = 0.5，正好是及格线，一分不多。** 原因是结构性的：
向量化只改变「怎么读这一列算距离」，**不改变「写了多少字节到盘上」和「占多少内存」**——
列式文件、mmap、WAL 的布局两边完全一样（两个数据目录的字节数一致到小数点后两位）。

**所以：题面 40% 的权重（I/O 20% + 内存 20%）在当前架构下就是 20 分的及格线，
一分都拿不到。** 要在这两项上得分，只能改存储结构（比如更紧凑的编码、少写 WAL），
那是另一个量级的工程。**这不是当前阶段该碰的东西**——先认清它值多少，
免得以为「优化 I/O」是低成本高收益。

于是完整图景是：

| 项 | 权重 | 状态 | 还能不能动 |
|---|---|---|---|
| 查询耗时 | 40% | f(R_q) = 0.9999，已饱和 | 动不了（再快一倍只值 +0.00003） |
| 写入耗时 | 20% | f(R_w) = 0.8521，**斜率最大** | **唯一值得动的** |
| I/O | 20% | f = 0.5000，R = 1 | 结构性问题，投入产出极低 |
| 内存 | 20% | f = 0.4994，R ≈ 1 | 同上 |

**性能项的真实上限是 0.95，而不是 1.0**——除非改存储结构。

## 四、判定标准（下次改完拿这张表比）

### 4.1 本机自测的合格线

测量口径必须是**多次独立进程 + 取最小值**，理由见 §5；
**且必须绑 2 核 + `OPENBLAS_NUM_THREADS=1`**（判题形态），理由见 §2.5。

```bash
# 判题形态的达标测量（当前版基线：最小值 0.0761 ms）
for i in $(seq 1 6); do
  OPENBLAS_NUM_THREADS=1 PYTHONPATH=seekdb/repo venv312/bin/python \
    seekdb/repo/tools/mvdb_bench_judge.py --rows 10000 --queries 1000 --cpus 18,19 --tag "chk_$i"
done
```

| 指标 | 达标线 | 优秀线 | 回归线 | 当前值 | 备注 |
|---|---|---|---|---|---|
| 本机 q（2 核，最小值口径） | **≤ 0.090 ms** | ≤ 0.078 ms | > 0.110 ms | **0.0761 ms** | 低于 0.090 才敢提测 |
| 本机 q（2 核，中位口径） | ≤ 0.100 ms | ≤ 0.088 ms | > 0.135 ms | **0.0877 ms** | 平台取三轮中位 |
| 本机 w（中位口径） | ≤ 0.70 s | ≤ 0.50 s | > 0.85 s | 0.637 s | 唯一还有余量的一项 |
| 协议地板（floor） | ≤ 0.030 ms | ≤ 0.025 ms | > 0.040 ms | 0.0248 ms | 管道往返，不归引擎 |
| 引擎净耗时 | ≤ 0.055 ms | ≤ 0.045 ms | > 0.070 ms | 0.0508 ms | q − floor |
| dot（2 核，BLAS=1） | ≤ 0.042 ms | ≤ 0.040 ms | > 0.050 ms | 0.0397 ms | 已达带宽上限 |
| 内核相对 numpy 路径 | ≥ 1.10× | ≥ 1.18× | < 1.05× | ~1.20× | 低于 1.05 说明内核没加载或没生效 |
| 材料合规（`mvdb_check_material.py`） | **PASS** | PASS | FAIL | PASS | 硬门槛，不通过直接被拒 |

**功能准入是一票否决**：任何一项 FAIL，总分 0，性能再高也没有意义。

### 4.2 折算到平台的门槛

`E平台 = (3.67/w + 2×664.335/q_plat) / 3`，其中 `q_plat = k × q_local`，
**k = 3.15（§2.2 两个观测点共同定标）**。

下表的"对应本机 q"全部按 **2 核判题形态**（绑 2 核 + BLAS=1）折算，
这是唯一能外推的配置（§2.5）：

| 目标平台 E | 需要的 q_plat | 对应本机 q（k=3.15） | 当前版达到了吗 |
|---|---|---|---|
| 1477.2（11-15 实测，无内核） | 0.3001 ms | 0.0953 ms | ✅ 早已超过 |
| **1871.70（11-16 实测，有内核）** | **0.2369 ms** | **0.0752 ms** | ✅ 刚好在这条线上 |
| **1917** | 0.2313 ms | 0.0734 ms | ✅ 达到了（0.0761 已接近） |
| **2100** | 0.2112 ms | 0.0670 ms | ❌ 未达到（当前 0.0761） |
| 2500 | 0.1775 ms | 0.0563 ms | ❌ 不可达 |
| 4300 | 0.1030 ms | 0.0327 ms | ❌ **物理不可达** |
| 5000 | 0.0885 ms | 0.0281 ms | ❌ **物理不可达** |
| 6000 | 0.0738 ms | 0.0234 ms | ❌ **物理不可达** |

**"物理不可达"的依据**（2 核形态下的成本分解）：

```
协议地板（管道往返）        0.0248 ms   ← 改不动：题面固定的一问一答
引擎净耗时                 0.0508 ms
  ├ dot（BLAS，2 核 1 线程）0.0397 ms   ← 已达带宽上限，float32 最优
  ├ topk（C 内核）          0.0133 ms
  ├ ctypes 调用             0.0091 ms
  ├ parse_text              0.0028 ms
  └ 未归因                  0.0067 ms
─────────────────────────
合计                       0.0761 ms
```

目标 5000 要 **0.0281 ms**——**比协议地板（0.0248 ms）只多 0.0033 ms**，
等于要求整个引擎（0.0508 ms）免费。**这个目标在 2 核判题形态下没有物理空间，应当放弃。**

> 这不代表性能项拿不到分。题面真正的 40 分走 `f(R)` 归一口径，
> 那一项早已饱和在 **0.9506**（见 §3.3），距离上限 1.0 只差写入侧那 4.9%。
> **平台原始分是线性代理量，不是那 40 分。**

**判读提测结果的口径**（按 k=3.15 折算当前版 0.0761 ms → 平台约 1850–1900）：

- 平台 E **≥ 1917** → 达到或超过上次提测水平，改进成立
- 平台 E 在 **1750 ~ 1917** → 与上次持平，检查是不是内核没被加载（查 Dockerfile 的 COPY 布局）
- 平台 E **< 1500** → 比 11-15 还差，说明有别的问题，**先查准入是否全绿**

按题面 f(R) 口径，E_题面 已经 0.9506，距离上限 1.0 只差写入侧那 4.9%。

## 五、测量方法：为什么必须取最小值

本机是个 20 核大小核的机器，而且**上面还跑着一个别的应用**（Isaac Sim，
线程会在核之间漂移，某轮采样时它的 214% CPU 正好压在我们绑定的核 19 上）。

结果是：

- 通用执行器基线：三轮 96.3811 / 96.3213 / 96.2816 ms，**波动 ±0.05%**——它纯 CPU，不碰 BLAS
- 快速路径：38 个单轮读数从 0.0785 抖到 0.1530 ms，**接近 2 倍**

差的不是代码，是被抢了。所以：

**标准测量命令（必须照做）**

```bash
# 一次独立进程，进程内 7 轮取中位数；重复 6 次；跨进程取最小值
for i in 1 2 3 4 5 6; do
  PYTHONPATH=seekdb/repo venv312/bin/python tmp/bench_ab.py --rounds 7 --tag "MIN$i"
done
```

**取最小值而不是中位数**，理由：干扰只会让数字变差，不会让它变好；最小值对应
「干扰最小的那个窗口」，是对本机能力上界的估计。

**不要用 `--cpus 0,1`。** `tools/mvdb_bench_judge.py` 的默认 `--cpus 0,1` 会用
`taskset` 把服务端钉在 0/1 两个核上，而这两个是小核（capacity 718，大核是 1017/1024）。
程序内的 `_pick_cores()` 只能在这个掩码里选，选不到大核，实测 q = 0.29 ms，是正确口径的 3 倍。
**要让程序自己选核（不传 `--cpus`）**，它会挑 [15, 19] 两个大核。

### 6.1 基准工具输出的三个数，各是什么

`tools/mvdb_bench_judge.py` 现在一次打印三个数，**它们不可互换**：

```
write 0.736 s   query 0.0918 ms/query   protocol floor 0.0250 ms   engine 0.0668 ms
  E local    4825   (this machine's q; optimistic by k)
  E platform 1533   (q_plat = 0.2892 ms = k 3.15 x 0.0918 ms; the number the judge prints)
  E=5000     needs query 0.0281 ms/query on this machine (protocol floor here is 0.0250 ms)
```

| 输出 | 含义 | 能不能当平台分 |
|---|---|---|
| `E local` | 用**本机** q 代进公式 `E=(3.67/w + 2×664.335/q)/3` | **不能**。它乐观了恰好 k 倍，量级会差 3 倍以上 |
| `E platform` | `q_plat = k × q_local`，k 默认 3.15，可用 `--platform-k` 改 | **能**。这是判题机打印的数 |
| `E=5000` | 达到平台分 5000 需要的**本机** q，和协议地板并排打印 | 用来一眼看出缺口，而不是靠推算 |

> **这一版为什么要改**：改之前工具把本机口径的数直接印成 `E estimate 4825`，
> 没有任何标注，很容易被当成平台分读成"已经过 5000"。这正是本项目在 §2.2
> 反复强调的口径混淆，工具自己不该再犯一次。现在三个数分列且各自标注，
> `E=5000` 需要的 0.0281 ms 与协议地板 0.0250 ms 直接并排，缺口在输出里自明。
>
> `--selftest` 会用两个已知的平台观测点（1871.704677 与 1477.2）校验投影公式，
> 容差 0.5% 相对误差——写入项从未在判题机上单独测过，是从本机带过去的，
> 而查询项比写入项大三个数量级，所以 0.5% 是诚实的上界。
