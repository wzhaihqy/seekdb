## 四、三处真实缺陷与修复

### 缺陷 1（头号嫌疑）：VARCHAR 长度按字节而非字符

- **要求**（README 功能项 13）：「VARCHAR 长度按 **Unicode 字符数**；字符串按 Unicode 码点序比较」。
- **原实现**（`minivectordb/core.py`）：

  ```python
  encoded = value.encode("utf-8")
  if column.length is not None and len(encoded) > column.length:   # ← 字节数
      raise SqlError(VALUE_OUT_OF_RANGE, ...)
  ```

- **后果**：`VARCHAR(16)` 存 16 个汉字（48 字节）会被误判超长而拒绝；存 16 个 ASCII 才刚好通过。
  公开用例 `sql_unicode` 只写了 '中文'（6 字节）所以没暴露，正式用例一旦打到长度边界就失败。
- **修复**：改为按字符数比较，字节数只用于存储编码。

  ```python
  encoded = value.encode("utf-8")
  # The declared length counts Unicode characters, not bytes: a
  # VARCHAR(16) holds sixteen Chinese characters, whose UTF-8 form is
  # 48 bytes long.  Counting bytes would reject a value the schema accepts.
  if column.length is not None and len(value) > column.length:
  ```

### 缺陷 2：UPDATE 的校验逐行进行，非法语句会「静默成功」

- **要求**（README 功能项 12）：「…**主键更新**…须返回约定错误」。
- **原实现**（`minivectordb/engine.py`）把主键更新检查写在遍历行的循环体内：

  ```python
  for pk, row in self._iter_rows(table):
      if where is not None and not _truthy(...):
          continue                      # ← 没匹配到行就整段跳过
      ...
      if new_pk != pk:
          raise SqlError(UNSUPPORTED_SQL, "updating the primary key is not supported")
  ```

- **后果**：`UPDATE docs SET id = 99 WHERE id = 1` 在**没有匹配行**时直接返回成功
  （`affected_rows: 0`），调用方无法区分「合法空操作」和「非法语句」。同理，SET 子句的
  类型错误（给 BIGINT 列赋字符串、给 VECTOR 列赋错维度）在空表上也不会报错。
- **修复**：把赋值列的解析、主键列的拒绝、值的类型校验全部提到扫描行之前，非法语句无条件失败。

### 缺陷 3：不支持类语句的错误码不一致

- **要求**：README 功能项 12 把 NULL / JOIN / 聚合 / 子查询 / ALTER / 外键 / 嵌套事务 / 主键更新
  列为同一类「不支持的语句」，「须返回**约定错误**」。公开题包 `sql_unsupported` 已确立该类用
  `unsupported_sql`。
- **原实现**：`ALTER`/`子查询` → `unsupported_sql`，但 `聚合`/`JOIN`/`外键`/`嵌套事务` → `syntax_error`，
  `NULL` → `constraint_violation`。
- **修复**：整类统一为 `unsupported_sql`。
